Дата: 7 сентября 2026 года. Редакция: 2, после повторного технического review и подготовки к передаче GPT-5.6 Luna. Статус: план реализации, код продукта ещё не создан.

Выбран пользователем вариант 2: отдельный MCP-сервер с редактором графов, локальной библиотекой версий и исполнением workflows в RunningHub. Дополнительно изучен официальный репозиторий `HM-RunningHub/ComfyUI_RH_OpenAPI`.

## 0. Как исполнять этот план

Этот документ — спецификация продукта. Порядок работы, журналирование и передача между сессиями закреплены в `PROGRESS.md` и разделах 0, 21–22 этого плана.

Работу вести небольшими проверяемыми пакетами из раздела 21. Разделы 1–19 описывают продукт, раздел 20 фиксирует точные контракты, разделы 21–22 — порядок реализации и доказательства готовности. Не пытаться реализовать все инструменты за один проход.

Единый журнал реализации — [PROGRESS.md](PROGRESS.md). В начале каждой сессии читать его; после каждого существенного шага реализации фиксировать выполненные изменения, проверки, результат и следующий шаг. Не откладывать запись до завершения всего пакета L00–L08. Подробный формат и правила — в разделе 22.1.

Нельзя заменять обязательный graph backend прямым вызовом стандартных API-моделей. Нельзя называть реализацию готовой на основании read-only MCP, mock-тестов или редактирования только скалярных inputs.

Без ключа и разрешённой live-пробы продолжать независимую локальную работу. Интеграционные проверки помечать `NOT_RUN`, не `PASS`. Отсутствие ключа блокирует доказательство облачного исполнения, но не создание редактора, хранения, MCP и recovery tests.

Граница версии 1 продукта: обычные API-графы из явно поддерживаемых нод, операции со связями и блоками, изображения/видео, LoRA flow и review loop. UI import/export поддерживается для перечисленного набора схем. Полная совместимость с неизвестными frontend-расширениями и custom nodes не заявляется.

## 1. Решение и ожидаемый результат

Взять за основу MCP-оболочку и инструменты каталога из `ComfyUI_RH_OpenAPI/developer-kit/mcp-server`. Развивать их в самостоятельный TypeScript MCP-сервер `runninghub` с собственными модулями графов, проектов, выполнения задач и проверки результатов.

Основной кандидат на исполнителя — RunningHub Workflow API с передачей полного API-format JSON. Обязателен хотя бы один доказанный RunningHub backend, исполняющий структурно изменённый граф. При подтверждённой непригодности Workflow API допустим проверенный ComfyUI proxy; причина выбора фиксируется. Инструменты поиска стандартных API-моделей из upstream дополняют эту возможность, но не заменяют её.

Пользовательский сценарий:

> Используй MCP RunningHub и сгенерируй изображение по сюжету и плану сцены 02b.

Агент самостоятельно:

1. Определяет проект и точную сцену.
2. Читает релевантные требования и находит необходимые утверждённые референсы.
3. Выбирает подходящий workflow или создаёт новый.
4. При необходимости добавляет и удаляет ноды, заменяет модели, перестраивает связи и блоки, меняет промпты и параметры.
5. Проверяет граф и доступность зависимостей, загружает нужные файлы и запускает генерацию.
6. Получает и сохраняет результат вместе с точным графом и параметрами запуска.
7. Показывает результат пользователю и останавливается до его ответа.

Команда на генерацию разрешает необходимую подготовку и запуск в пределах установленной политики проекта. Не вводить обязательное повторное подтверждение каждого промпта, подключения ноды или обычного запуска. Утверждение качества происходит после получения результата. Выбор этого плана сам по себе не является командой на платную тестовую генерацию.

## 2. Область реализации

### Обязательные возможности

- Создание workflow с нуля, из локального файла, из библиотеки либо из доступного RunningHub workflow ID.
- Добавление, удаление, замена и соединение нод; изменение значений входов.
- Создание, вставка, замена и удаление функциональных блоков из нескольких нод.
- Работа с промптами, seed, sampler, scheduler, steps, CFG, denoise, размером изображения, длительностью, FPS и другими реально поддерживаемыми параметрами.
- Выбор совместимых checkpoint, diffusion model, VAE, text encoder, LoRA и управляющих компонентов в пределах возможностей среды исполнения.
- Загрузка изображений, масок и видео; сопоставление референсов с нужными входами графа.
- Генерация изображений и видео, получение статуса, результатов и диагностики; отмена там, где она подтверждена API.
- Локальные версии графов, история изменений, результаты, отзывы пользователя и восстановление после перезапуска.
- Несколько независимых проектов с разными сценами, структурами папок и референсами.

### Границы выбранного варианта

- Локальный сохранённый workflow и workflow в облачном Workspace — разные сущности. Автоматическое создание, переименование и сохранение объектов Workspace не входят в вариант 2.
- Добавить существующий класс ноды в JSON и установить новый Python-пакет custom nodes на сервер — разные операции. Вторую не обещать без поддерживаемого механизма RunningHub.
- Выбор доступной модели и загрузка произвольных весов на сервер также различаются. Отдельно поддержать официальный механизм загрузки LoRA; остальные способы добавления весов требуют доказанной поддержки.
- Браузерная автоматизация, локальная GPU-генерация, монтаж фильма, озвучка и публикация результатов не входят в обязательную поставку.
- Редактор графов входит в обязательную поставку. Прототип, умеющий только менять промпты и запускать API-модель, не считается выполнением этого плана.

## 3. Проверенные сведения об API

Состояние «документировано» означает наличие описания в официальном источнике; оно не означает успешной проверки с ключом пользователя.

| Возможность | Найденное основание | Решение для реализации |
| --- | --- | --- |
| Запуск полного графа | Advanced Workflow API принимает строковое поле `workflow`, имеющее приоритет над `workflowId` | Основной путь структурного редактирования; проверить на реальных изменениях графа |
| Замена параметров | `nodeInfoList` адресует `nodeId` и `fieldName` | Использовать для подходящих параметров, не выдавать за общий редактор |
| Референсы для workflow | Upload возвращает серверный `data.fileName` | Подставлять в проверенный loader; не превращать путь в выдуманный URL |
| Загрузка LoRA | Отдельный upload flow для `RHLoraLoader` | Добавить как отдельную возможность, не смешивать с обычным upload медиа |
| Группы редактора | Логика frontend-групп не поддерживается через `nodeInfoList` | Компилировать функциональные блоки в конкретный граф |
| ComfyUI proxy | Документированы `/proxy/<key>` и `/proxy-plus/<key>` | Дополнительный адаптер только после проверки нужных маршрутов |
| Workspace CRUD | Полный публичный контракт не найден | Локальное сохранение и экспорт; облачное сохранение не заявлять |

Источники: [полный граф при запуске](https://www.runninghub.ai/runninghub-api-doc-en/api-425761093), [nodeInfoList и группы](https://www.runninghub.ai/runninghub-api-doc-en/doc-8287464), [загрузка ресурсов](https://www.runninghub.ai/runninghub-api-doc-en/api-425761099), [LoRA](https://www.runninghub.ai/runninghub-api-doc-en/api-425761100), [ComfyUI proxy](https://www.runninghub.ai/runninghub-api-doc-en/doc-8287466).

Разделить семейства API. Workflow API и Standard Model API имеют разные операции загрузки, запросы и ответы. Для прямого Model API документация указывает Enterprise-Shared ключ; наличие ключа для workflows не доказывает доступ к прямым моделям. Проверять тип и доступность при подключении. [Типы API и ключей](https://www.runninghub.ai/runninghub-api-doc-en/).

### 4.3. Обнаруженные ограничения

1. Каталоги рассинхронизированы: основной JSON содержит 411 записей, публичный JSON — 383, текстовый `capabilities.md` сообщает 365. Это количества записей в конкретных файлах, а не проверенная доступность моделей у пользователя.
2. Сборка MCP `npm run build` прошла на Node `v22.18.0`. `npm test`: 7 тестов, 5 успешных, 2 неуспешных. Падения связаны с ценовыми ожиданиями: `0.05` против `0.07` и `0.2` против `1.5`. Эти значения описывают тесты и snapshot каталога, а не актуальную стоимость генерации.
3. Проверка payload в TypeScript проверяет базовые типы, enum и URL, но не обеспечивает полную проверку числа референсов, размеров медиа, диапазонов и сочетаний параметров. В частности, пустой массив медиа не считается отсутствующим обязательным входом.
4. Python-отправка задач допускает повторные submit после сетевых ошибок. Для нашей системы это создаёт риск повторной генерации при потерянном ответе; логику необходимо изменить.
5. `core/base.py` импортирует `torch` и `numpy`, преобразует ComfyUI media types и использует прогресс ComfyUI. Это лишняя зависимость для самостоятельного MCP, исполняющего графы в облаке.
6. Режим `skip_error` способен возвращать изображение/видео-заглушку после ошибки. Такой результат нельзя принять за успешную генерацию.
7. Python-код пишет логи через `print`; его прямое выполнение внутри stdio MCP потребовало бы перенаправления логов. `_sanitize_payload` в `core/task.py` в основном сокращает строки, что не равно полной очистке чувствительных полей.

Основания: [тесты MCP](https://github.com/HM-RunningHub/ComfyUI_RH_OpenAPI/blob/6dc03fd9655bb8729a561c5f5a1f73c4b285081d/developer-kit/mcp-server/tests/mcp-tools.test.mjs), [валидация](https://github.com/HM-RunningHub/ComfyUI_RH_OpenAPI/blob/6dc03fd9655bb8729a561c5f5a1f73c4b285081d/developer-kit/mcp-server/src/validation.ts), [submit и polling](https://github.com/HM-RunningHub/ComfyUI_RH_OpenAPI/blob/6dc03fd9655bb8729a561c5f5a1f73c4b285081d/core/task.py), [база нод](https://github.com/HM-RunningHub/ComfyUI_RH_OpenAPI/blob/6dc03fd9655bb8729a561c5f5a1f73c4b285081d/core/base.py).

### 4.4. Итоговое архитектурное решение

Использовать подкаталог `developer-kit/mcp-server` как исходную кодовую базу самостоятельного сервера. Не делать runtime-форк всего ComfyUI-плагина. Сохранить полезные инструменты и добавить полноценный Workflow API backend и graph engine.

На этапе реализации оформить происхождение переносимых файлов в `UPSTREAM.md`, сохранить лицензию, закрепить commit и хэши данных. Обновления upstream импортировать отдельно, с diff схем и регрессионными проверками. Не автоматически обновлять модели или изменять утверждённые workflows вслед за `main`.

Опциональный прямой Model API adapter можно добавить после основного графового сценария. Он должен явно называться `standard_model`, иметь отдельные ограничения и не маскироваться под выполнение произвольного ComfyUI workflow.

## 5. Архитектура продукта

```text
Агент пользователя
  │ MCP stdio: выбор, анализ, редактирование, запуск, показ результата
  ▼
RunningHub MCP — TypeScript
  ├─ Project context: проекты, планы, сцены, референсы
  ├─ Catalog: workflows, блоки, ноды, модели, совместимость
  ├─ Graph engine: import → edit → validate → compile → revision
  ├─ Execution service: подготовка, загрузки, запуск, восстановление
  ├─ Review service: результат → ожидание → отзыв/утверждение
  ├─ SQLite: задания, версии, зависимости, статусы, события
  └─ Backend adapters
       ├─ RunningHub Workflow API — основной кандидат на graph backend
       ├─ RunningHub ComfyUI proxy — альтернатива по результатам проверки
       └─ Standard Model API V2 — опциональный отдельный режим
```

Основной runtime: Node.js + TypeScript, официальный MCP SDK, схемы Zod, SQLite и локальные JSON/media-файлы. Выбрать поддерживаемую LTS-версию Node и закрепить версии зависимостей при реализации. Успешная текущая сборка upstream на Node 22.18.0 не заменяет проверку целевой поставки.

MCP выполняет детерминированные операции. Творческие решения, интерпретацию произвольного MD-плана и визуальный анализ выполняет подключённый агент. Отдельный скрытый LLM внутри сервера не требуется.

Статусы и manifest сохраняются до возврата ответа инструментом. Пока процесс MCP активен, execution service опрашивает известные задачи. Если клиент закрыл процесс, при следующем старте сервер восстанавливает наблюдение из SQLite; генерация на RunningHub может продолжаться независимо. Отдельный Windows service не требуется для первой версии.

Без работающего клиента этот MCP не обещает сам отправить сообщение в чат. После повторного подключения `rh_job`/`rh_get_results` обнаруживают готовый результат и предлагают агенту показать его. Не добавлять расписания, фоновые Windows services или второй LLM, чтобы скрыть эту границу первой версии.

## 6. Проекты, сцены и референсы

### 6.1. Подключение проекта

Подключение по корневой папке выполняется один раз. Конфигурация проекта задаёт документы сюжета/плана, каталоги референсов, выходную папку, предпочтения workflows и правила генерации. Текущий проект передаётся явным `project_id` во все изменяющие операции, чтобы параллельные диалоги не смешивали данные.

Глобальный пользовательский реестр хранит только пути и настройки подключения. SQLite хранит operational state; файлы проекта остаются у пользователя. Внутри `.runninghub/` проекта сохранять переносимые manifest, версии и снимки входных требований.

### 6.2. Разбор произвольного плана

- MCP индексирует документы и возвращает агенту релевантные фрагменты с `source_path`, заголовком и hash содержимого.
- Агент формирует нормализованную запись сцены; сервер проверяет её структуру и существование файлов.
- `02b`, `02B`, `scene_02B` могут быть alias одной сцены, если это однозначно следует из проекта. Конфликт alias возвращается как неоднозначность, не выбирается случайный файл.
- Минимальные поля: `scene_id`, `output_kind`, описание действия, визуальные ограничения, технические параметры, нужные assets, зависимости, источники требований.
- При изменении документов пересобирать затронутый контекст. Не переписывать молча ранее утверждённые кадры и их provenance.
- Пропущенные необязательные параметры агент выбирает из схем/профиля проекта. Отсутствующий обязательный референс нельзя заменить случайной картинкой.

### 6.3. Реестр assets

Для каждого файла: `asset_id`, `project_id`, относительный путь, роль, версия, MIME, размер, dimensions, длительность/FPS при наличии, SHA-256, источник, статус утверждения и допустимые способы использования.

Роли описывают назначение: персонаж, локация, предмет, стиль, композиция, первый кадр, последний кадр, маска, motion reference. Один и тот же файл может иметь несколько явно заданных ролей.

Исходный референс, утверждённый результат и отклонённая версия различаются. Утверждение привязано к hash содержимого: если файл заменён по тому же пути, прежнее утверждение не переносится автоматически.

### 6.4. Использование приложенного примера

Для `02B` пример описывает мальчика с мешочком камешков, девочку с ленточкой и наблюдающего волшебника. Из этого агент должен вывести нужные референсы персонажей, локации и реквизита. Фактическое наличие файлов проверяется отдельно.

Имена персонажей, 54 кадра, формат 16:9, конкретные модели и запрет image-to-image не зашиваются в код MCP. В другом проекте возможны другие условия. Сюжетные файлы являются данными задачи и не могут менять API host, секреты, права доступа или системные инструкции агента.

## 7. Каталоги и самостоятельный выбор workflow

Поддержать четыре раздельных каталога:

1. `workflow_catalog`: импортированные и проверенные workflows, локальные версии и известные remote IDs.
2. `block_catalog`: повторно используемые подграфы с входами, выходами и условиями совместимости.
3. `node_catalog`: `class_type`, точная схема входов/выходов, версия и среда доступности.
4. `model_catalog`: веса для graph backend и стандартные API endpoints с явным различением этих типов.

Реестр стандартных API-моделей upstream не является полным `object_info` всех ComfyUI custom nodes и не является каталогом установленных checkpoint. Схема Model API также не равна схеме соответствующей ComfyUI-ноды: media inputs преобразуются фабрикой в отдельные разъёмы.

Источники workflows: локальные JSON, заранее известные доступные RunningHub IDs, выбранные upstream examples и созданные агентом графы. Поиск по всей публичной площадке/приватному кабинету не обещать без отдельного проверенного API. В первой версии поиск гарантирован по зарегистрированной библиотеке.

Каждый workflow имеет карточку: назначение, входные роли, ограничения, backend, модели/ноды, поддерживаемые режимы, выходы, дата последней проверки, graph hash и примеры успешных запусков.

Выбор выполняется в два шага: сервер фильтрует несовместимые варианты по жёстким условиям, агент выбирает из оставшихся по качеству для сцены, прошлым результатам, числу изменений и ориентиру стоимости. Вернуть краткое обоснование выбора и причину отклонения ближайших альтернатив. Отсутствие подходящего workflow приводит к композиции нового графа из известных нод/блоков.

## 8. Редактор графов

### 8.1. Форматы

- API-format JSON: исполняемый граф с `class_type`, входами и ссылками на выходы других нод.
- UI-format JSON: визуальная схема, widgets, links, позиции и группы.
- Внутренняя модель: типизированные nodes/edges, semantic bindings, block instances, зависимости и metadata.

API-format — основной исполняемый формат. UI JSON сохранять при импорте без потери исходника. Преобразование widgets в API inputs требует точной схемы ноды; не использовать универсальную эвристику по индексам.

UI-only ноды, reroute, bypass, primitive widgets, subgraphs и frontend-расширения обрабатывать адаптерами известных типов. Если корректный экспорт не доказан, вернуть конкретную неподдерживаемую конструкцию и возможность использовать API-export. Не отбрасывать её молча.

Для поддержанных классов обеспечить экспорт UI JSON с генерируемой раскладкой. Сохранение исполняемого JSON остаётся доступно даже при отсутствии UI-адаптера.

### 8.2. Обязательные операции

| Операция | Требуемое поведение |
| --- | --- |
| `add_node` | Создать уникальный ID; заполнить допустимые defaults из схемы |
| `remove_node` | Показать затрагиваемые связи; потребовать явную стратегию перенаподключения зависимых нод |
| `replace_node` | Сопоставить входы/выходы; явно указать несовместимые параметры |
| `set_input` | Проверить тип, диапазон и существование входа |
| `connect` / `disconnect` | Проверить существование разъёмов и совместимость типов |
| `insert_block` | Перенумеровать внутренние IDs и связать публичные порты |
| `replace_block` / `remove_block` | Сохранить согласованные внешние связи либо вернуть конфликт |
| `bind_asset` | Назначить локальный asset логическому media-входу до upload |
| `set_model` | Проверить семейство, loader, связанные encoder/VAE/LoRA |

Предоставить пакетную транзакцию `rh_edit_workflow`: список типизированных операций, `base_revision`, причина изменения. Либо применяются все операции, либо версия остаётся прежней. Вернуть diff, новую revision и отчёт проверки.

**Черновик разрешён.** Пустой создаваемый граф, неподключённый обязательный вход и временное отсутствие output node допустимы при сохранении revision со статусом `DRAFT`. Некорректный тип значения, неизвестный порт, дублирующийся ID и ссылка на удалённую ноду недопустимы даже в черновике. Перед запуском нужна полная проверка `runnable`. Иначе последовательность «создать → добавить → соединить» была бы невозможна.

Проверка целостности выполняется после всего пакета операций: допустимо внутри одного пакета удалить ноду и затем перенаподключить потребителей. Если итог содержит висячую ссылку, пакет отклоняется. Неподключённый порт хранится как отсутствие значения, а не как ссылка на несуществующий объект.

Массив в inputs не всегда является ссылкой. Различать literal arrays и `[node_id, output_index]` по схеме и явному типу внутреннего значения. Не запрещать все массивы и не трактовать каждый массив как edge.

### 8.3. Функциональные блоки

Блок — версия подграфа с именованными входами/выходами, параметрами и зависимостями. Примеры: подготовка референса, загрузчик модели с encoder/VAE, conditioning, sampler, upscale, сборка видео.

Включение/выключение блока означает конкретную перестройку графа. Обход возможен только с заданным отображением входов на выходы. Визуальная группа служит оформлением; она не должна быть единственным механизмом управления исполнением.

Каждый экземпляр блока владеет отдельным набором внутренних node IDs; общие внешние ноды не считаются его собственностью. Удаление блока не удаляет общую модель/референс соседнего блока. Для `set_model` другого семейства нужен известный replacement block и port mapping; произвольную конверсию архитектур не изобретать.

### 8.4. Проверки перед запуском

1. Структура: IDs, существующие ссылки, обязательные inputs, достижимость нужных output nodes.
2. Типы: совместимость разъёмов, enum, диапазоны, literal values.
3. Семантика: соответствие модели её loaders/encoders, режимам reference/start/end, frame-grid правилам и размерам.
4. Среда: наличие классов/весов в целевом backend на основании актуальных данных.
5. Проект: только нужные допустимые assets, утверждённые зависимости, выбранная сцена и ограничения плана.
6. Исполнение: количество платных стадий, batch, instance и наличие незавершённой проверки результата.

Неизвестную runtime-совместимость показывать как `unknown`, а не как «проверено». Для первой версии неподдерживаемые циклические/control-flow конструкции отклонять с указанием причины; не объявлять все возможные ComfyUI графы простыми DAG.

Возвращать три независимых результата: `structural`, `runnable`, `backend_compatibility`. Режим production использует подтверждённый профиль совместимости. Режим `capability_test` позволяет в рамках разрешённой пользователем live-пробы проверить неизвестную доступность при известных схемах и валидном графе. Неизвестная схема входа не становится известной от разрешения теста. Успех одного графа подтверждает протестированную комбинацию, а не все комбинации его нод и моделей.

## 9. Модели и доступность custom nodes

Графовый редактор должен уметь менять модель целиком, включая связанные ноды и conditioning. Замена имени файла допустима только при совместимости архитектур.

Схемы нод получать из проверенного remote discovery, если он доступен. Резервный источник — закреплённые схемы для поддерживаемых пакетов и вручную проверенные fixtures с явно указанной средой. Не использовать локальный ComfyUI `object_info` как доказательство облачной доступности.

Если нужной ноды нет, агент ищет функционально совместимый блок или другой workflow. Если решения в рамках требований нет, сообщает точную недостающую зависимость. Не притворяться, что Python custom node установлен редактированием JSON.

Для собственных LoRA реализовать вычисление требуемого API хэша, получение upload URL, загрузку, сохранение provider reference и привязку к `RHLoraLoader`. Удаление LoRA из графа не должно удалять исходный файл или облачный объект.

Запуск примера с `RH_OpenAPI_*` возможен только после проверки наличия нужного класса и конфигурации ключа на исполнителе. Не встраивать секрет в `RHSettingsNode` и не пересылать ключ внутри общего workflow JSON. Если облачный плагин не имеет подходящего механизма конфигурации, этот путь остаётся недоступным; обычные поддержанные ComfyUI workflows должны работать независимо от него.

## 10. Подготовка и исполнение

### 10.1. Раздельные adapters

Workflow adapter включает получение API-графа, upload, full-graph submit, status, outputs и cancel. Зафиксировать реальные request/response fixtures для каждого маршрута, включая HTTP 200 с прикладной ошибкой. ID хранить строками без потери точности JavaScript.

Проверять точность **до** обычного `JSON.parse`: node/task/workflow IDs и seed могут приходить JSON-числами вне `Number.MAX_SAFE_INTEGER`. Выбрать lossless JSON codec, закрепить зависимость и проверить round-trip. Внутренний decimal integer хранить строкой с тегом типа; при отправке сериализовать согласно схеме провайдера как точный numeric token либо строку. `String(JSON.parse(...).id)` не восстанавливает уже потерянные цифры. Не менять все числовые поля API на строки.

Из документации advanced submit остаётся проверить сочетание обязательного `workflowId` и переданного `workflow`: допускается ли отсутствие ID либо необходим доступный базовый ID. Это первый интеграционный эксперимент, не предположение, скрытое в коде.

Если потребуется proxy, проверять по одному конкретному маршруту. Совместимость `/prompt` не доказывает наличие `/object_info`, `/history`, `/ws`, `/interrupt` и загрузки моделей. Секрет в proxy URL очищать из логов.

Standard Model adapter при добавлении использует отдельный upload URL flow и `/query`. Не смешивать его `download_url` с workflow `fileName`. Описанный в upstream V2-контракт использовать как исходный материал с собственными fixtures. [Контракт developer-kit](https://github.com/HM-RunningHub/ComfyUI_RH_OpenAPI/blob/6dc03fd9655bb8729a561c5f5a1f73c4b285081d/developer-kit/rh-api-contract.md).

### 10.2. Подготовка

`rh_prepare_generation` фиксирует сцену, версию графа, bindings референсов, параметры, ожидаемые выходы и объём исполнения. Не отправляет платную задачу. Обычная последовательность агента автоматически вызывает submit после успешной подготовки; отдельный вопрос пользователю не требуется.

Перед upload повторно проверить asset hashes и текущую версию входных требований. После upload создать точный отправляемый JSON с серверными ссылками. Сохранить два hash: логического графа с asset bindings и окончательного payload. Подмена ссылок при upload — ожидаемая стадия компиляции, а не изменение творческого задания.

Execution plan ссылается на конкретную неизменяемую revision, а не на `latest`. Новая revision рядом со старой не меняет уже подготовленный план; пользовательская правка активного задания отменяет старый plan и создаёт новый. Повторная проверка перед отправкой обнаруживает изменённые assets, требования, политику и статус отмены. Сам отправляемый граф всегда берётся из snapshot плана.

Seed задавать явно согласно текущему контракту RunningHub. Изученная документация предупреждает о переустановке seed при API-вызове; если для сохранения требуется `nodeInfoList`, генерировать эти overrides из того же graph snapshot. Проверить их приоритет совместно с `workflow`, исключить расходящиеся seed в двух полях. [Примечания к nodeInfoList](https://www.runninghub.ai/runninghub-api-doc-en/doc-8287464).

Ограничения файлов брать из выбранного маршрута и модели. В документации workflow upload есть несогласованность между текстовым лимитом 30 MB и примером ошибки 10 MB; зафиксировать проверенный лимит в capabilities. Не сжимать и не обрезать референс скрытно. Если преобразование разрешено проектом, сохранить производный файл и запись о нём.

### 10.3. Состояние задачи и повторные вызовы

```text
execution: PREPARED → UPLOADING → READY → SUBMITTING → TRACKING
                                          └─ SUBMIT_UNKNOWN
provider:  UNKNOWN → QUEUED/RUNNING → SUCCEEDED | FAILED | CANCELLED
artifacts: NOT_STARTED → DOWNLOADING → READY | DOWNLOAD_FAILED
review:    NOT_READY → PENDING_REVIEW → APPROVED | CHANGES_REQUESTED | REJECTED
```

`POLL_PAUSED`, `DOWNLOAD_FAILED`, `CANCEL_REQUESTED` и `CANCEL_UNKNOWN` хранить отдельно от окончательного статуса провайдера. Таймаут ожидания MCP не означает, что генерация завершилась ошибкой или отменена.

Каждый submit имеет локальный request ID и атомарную запись в SQLite до сетевого обращения. Повторный вызов с тем же ID возвращает существующую задачу. Это локальная защита; она не доказывает provider-side exactly-once.

Один execution plan допускает максимум один job: уникальный `plan_id` предотвращает повтор даже с другим request ID. В транзакции сначала искать существующий job, затем проверять chain lock, лимиты и актуальность плана. Вторая транзакция атомарно меняет `READY` на `SUBMITTING` и сохраняет submit intent; только выигравший процесс выполняет HTTP POST. Транзакцию SQLite не держать открытой на время сетевого запроса.

При рестарте `SUBMITTING` без task ID переводится в `SUBMIT_UNKNOWN`, даже если процесс мог упасть до фактической отправки. Это сознательная потеря автоматического повтора ради отсутствия возможного дубликата. Если task ID сохранён, возобновлять polling. Повторить download можно без повторения submit. Подробные сценарии конкурентности — в разделе 20.

После неоднозначного ответа не делать автоматический повтор платного POST и не переключать backend. Сначала пытаться восстановить состояние по известному task ID и доступным официальным механизмам. Если ID потерян и API не позволяет однозначную сверку, сохранять `SUBMIT_UNKNOWN` и сообщать необходимость решения пользователя. Hash запроса без серверного поиска сам по себе ничего не восстанавливает.

Polling и скачивание повторять с ограниченным backoff. Ожидание инструмента ограничить, например, 30 секундами, возвращая актуальный статус и handle для следующего запроса. Прогресс в процентах выводить только при наличии provider evidence; прошедшее время не выдавать за реальный процент выполнения.

### 10.4. Границы автономности

По умолчанию одна генерационная заявка пользователя создаёт один результат для проверки. До её утверждения не запускать следующую сцену или эстетические перегенерации «на улучшение». По запросу нескольких вариантов допускается один явно заданный review batch.

Один workflow может содержать несколько платных model nodes. Подготовка обязана учитывать это: ограничение только количества API-submit не ограничивает число внутренних платных операций. Разбивать workflow в местах, где план требует отдельного утверждения промежуточного изображения, например перед его анимацией.

Лимиты проекта: число результатов/стадий, batch, длительность, разрешение и параллельность; денежный лимит — дополнительный, если расчёт подтверждён. Не выдавать предварительную оценку за гарантированный потолок стоимости. Если пользователь установил жёсткий денежный потолок, а его соблюдение нельзя обеспечить, сообщить это до запуска.

## 11. Результаты и ожидание подтверждения

Для результатов использовать отдельное состояние проверки:

```text
PENDING_REVIEW → APPROVED
               → CHANGES_REQUESTED → новая версия → PENDING_REVIEW
               → REJECTED
```

Успешный статус API не означает утверждение пользователем. Инструмент записи отзыва принимает ID конкретного результата, решение и текст обратной связи. Агент вызывает его только на основании ответа пользователя; MCP не должен выдавать модельный `approved: true` за независимое доказательство человеческого согласия.

Review gate проверяется в общем execution service, включая низкоуровневый запуск произвольного workflow. Импорт графа под новым именем не должен обходить незавершённую проверку в той же производственной цепочке. Пользователь может явно изменить режим или переключить задачу; это фиксируется отдельным событием.

Цепочка идентифицируется `project_id + chain_id`; она создаётся сервером через `rh_work_item`, а scene ID и имя workflow её не заменяют. Состояние цепочки хранится в БД и защищает также период выполнения/скачивания. Все submit требуют `work_item_id`; инструментов, запускающих граф в обход этой проверки, не публиковать. При `CHANGES_REQUESTED` старый job остаётся неизменным, следующее явно запрошенное исправление получает новый work item в той же цепочке.

Утверждение результата само по себе не является командой на следующую генерацию, если пользователь не задал последовательный пакет/продолжение. `REJECTED` без просьбы исправить не запускает замену автоматически. Это рабочий процесс доверенного локального агента, а не криптографическая аутентификация речи пользователя; `user_message_ref` хранит происхождение решения, не доказывает его серверу независимо от клиента.

После завершения:

1. Скачать все нужные выходы с временным именем, проверить MIME/размер/декодирование и атомарно завершить сохранение.
2. Сохранить оригинальные файлы. Preview, poster и contact sheet — отдельные производные assets.
3. Вернуть MCP image content или resource link с поддерживаемым клиентом preview; для видео — файл/ссылка и poster. Не считать один текстовый URL полноценным показом изображения, если клиент позволяет отображение.
4. Для видео проверить metadata и, при доступном визуальном анализе агента, кадры/движение. Если агент не умеет просматривать видео, честно разделять техническую и визуальную проверку.
5. Сообщить пользователю результат, версию и существенные отклонения. Остановиться до ответа.

При изменениях создать новую версию, сохранить исходную и использовать отзыв как новое требование. Не переносить утверждение на новую версию и не использовать отклонённый результат как референс без явного указания.

## 12. Контракт инструментов MCP

Сохранить шесть upstream-инструментов каталога, расширив их проверку и обозначив область `standard_model`. Дополнить следующими инструментами. Названия — проектируемый интерфейс, а не уже существующие инструменты.

| Инструмент | Основной вход | Результат |
| --- | --- | --- |
| `rh_get_capabilities` | profile/backend | Доступность API, ограничения, доказательства и даты проверок |
| `rh_project` | action: register/list/inspect/index; project ID/path | Конфигурация и индекс документов/assets |
| `rh_scene` | action: resolve/read/upsert; project ID, scene ID | Нормализованные требования и ссылки на источники |
| `rh_work_item` | action: create/read/close; project/scene, chain, user request | Единица запрошенной работы и её связь с review-цепочкой |
| `rh_search_workflows` | Требования сцены и фильтры | Ранжированные совместимые карточки |
| `rh_import_workflow` | local path либо remote ID | Локальный workflow и отчёт импорта |
| `rh_create_workflow` | Имя, API graph либо стартовая схема | Первая revision локального графа |
| `rh_get_workflow` | workflow ID, revision | Граф, bindings, зависимости и краткое описание |
| `rh_get_node_schema` | class type, backend, schema revision | Проверенная схема и статус доступности |
| `rh_search_nodes` | Назначение, типы портов, backend | Кандидаты нод с совместимостью |
| `rh_search_graph_models` | Семейство, loader, backend | Доступные веса/модели для графов |
| `rh_block` | action: list/read/create; block data | Версионируемый подграф с портами |
| `rh_edit_workflow` | base revision, operations | Новая revision, diff, validation |
| `rh_validate_workflow` | workflow revision, backend | Ошибки, предупреждения и неизвестная совместимость |
| `rh_export_workflow` | revision, API/UI format | Локальный JSON без секретов |
| `rh_asset` | action: inspect/register/prepare/upload | Asset metadata или provider reference |
| `rh_upload_lora` | Зарегистрированный файл и профиль | Проверенный LoRA reference |
| `rh_prepare_generation` | work item ID, workflow revision, bindings | Неизменяемый execution plan и проверки |
| `rh_run_workflow` | execution plan ID, request ID | Durable job handle и provider task ID при наличии |
| `rh_job` | action: status/wait/resume/cancel; job ID | Нормализованный статус и диагностические данные |
| `rh_get_results` | job ID | Локальные результаты, previews и manifest |
| `rh_review_result` | result ID, решение, отзыв | Состояние проверки и разрешённый следующий шаг |

Общий ответ: `ok`, `data`, `warnings`, `error`, `next_actions`. Ошибки должны включать машинный код, контекст ноды/поля, recoverability и предложенное исправление. Не возвращать секреты, огромный полный каталог или stack trace вместо полезного объяснения.

На уровне MCP не скрывать неуспех внутри внешне успешного text result: ошибки исполнения инструмента помечать `isError=true`; в структурном результате `ok=false`. Отчёт валидации с найденными проблемами сам по себе может быть успешным вызовом инструмента, но `runnable` остаётся `draft`/`invalid`. Включить тесты обеих ситуаций через MCP transport.

Схемы tools делать строгими: typed discriminated unions для действий и graph operations; unknown fields отклонять там, где они могут повлиять на выполнение. JSON Schema описания инструментов и фактическая валидация должны совпадать.

## 13. Хранение, воспроизводимость и защита данных

Предлагаемая структура внутри подключённого производственного проекта:

```text
.runninghub/
  project.json
  scenes/
  assets/index.json
  workflows/<workflow-id>/<revision>/
    source.json
    graph.api.json
    graph.ui.json             # только при поддержанном экспорте
    metadata.json
    validation.json
  runs/<run-id>/
    plan.json
    submitted-workflow.json
    manifest.json
    review.json
generated/runninghub/<scene-id>/<version>/
  original/
  preview/
```

Operational database разместить в пользовательской папке данных приложения. В ней хранить проекты, jobs, requests, graph revisions, upload cache, review events и dependencies. Manifest проекта должен позволять восстановить связь с результатами без исходной базы.

Во время работы БД — источник operational state. Файловые snapshots immutable; manifest — его переносимый экспорт. Атомарную общую транзакцию SQLite+filesystem не обещать: сначала сохранить immutable blob через temporary file и rename, затем ссылку/событие в БД; повторяемую публикацию manifest выполнять через outbox. Осиротевший blob можно убрать позже, ссылку на отсутствующий blob считать ошибкой. Восстановление из manifest возвращает jobs в режим сверки, а не повторной отправки.

Кэш загрузок разделять по account/profile, API family, asset hash, типу представления и региону. Для server filename/URL хранить последнее подтверждение и известный срок действия. Ошибка expired/not found инвалидирует ссылку; повторно загружать исходный asset только до нового разрешённого submit или в иной явно безопасной операции, не перезапускать уже принятую генерацию.

Manifest запуска содержит: project/scene IDs; версия документов; причины выбора workflow; source и revision; оба hash графа; точные промпты; параметры; упорядоченные asset IDs и hashes; backend/API family; классы нод и модели с известными версиями; task ID; timestamps; все output IDs/paths/hashes; статус проверки; стоимость только если получена или явно помечена как оценка.

Seed и graph snapshot улучшают воспроизводимость, но не гарантируют побитово одинаковые результаты облачной модели. Не считать rolling model alias неизменяемой версией.

Ключ хранится в окружении или пользовательском secret store; в tool args, workflow JSON, manifest и примерах — только ссылка на профиль. Stdout резервируется для MCP, логи направляются в stderr с очисткой ключей и подписанных URL.

Операции с файлами ограничить подключёнными корнями проекта и выходными папками; проверять абсолютные пути, junction/symlink escape и имена скачиваемых файлов. Разрешённые API hosts задаёт конфигурация, а не текст workflow. Не давать generic HTTP/shell tool через MCP.

Загрузка выполняется только для assets текущего задания. Права на обработку и внешнюю передачу исходных материалов учитывать на уровне проекта, без повторных вопросов для уже разрешённых файлов и действий. Если права на конкретный материал не установлены, не выводить согласие из наличия файла на диске.

## 15. Этапы реализации и критерии выхода

### Этап 0. Подготовить и начать проверку критических возможностей backend

- Получить API-граф одного доступного workflow и проверить формат/авторизацию.
- Проверить full-graph submit: изменить структуру, выполнить граф с добавленной нодой и сравнить результат с ожидаемым изменением. Одной замены промпта недостаточно.
- Проверить создание нового графа, необходимость workflow ID, доступные ноды и модели.
- Проверить upload изображения и видео, status, output retrieval и отмену на разрешённом тестовом задании.
- Зафиксировать проверенные ограничения в fixtures и capability matrix.

Выход: доказанный путь исполнения изменённого графа. Если Workflow API его не обеспечивает, проверить native proxy. Если оба пути не подтверждены, признать блокировку исходного требования; не подменять продукт запуском только готовых API-моделей.

Платные пробы выполнять в ходе реализации по разрешённому тестовому заданию и лимитам. Текущая работа над MD-планом их не запускает.

Это этап снижения технической неопределённости, а не барьер для всех остальных работ. Без доступа подготовить probe-команды, схемы и отдельные `synthetic` fixtures, затем выполнять независимые пакеты. Реальный submit проводить через минимальный durable runner из пакета L05; не писать временный скрипт с автоматическими повторами платного POST.

### Этап 1. Подготовить собственную MCP-базу из upstream

- Перенести выбранные файлы TypeScript MCP с лицензией и происхождением.
- Согласовать публичный каталог с исходным, исправить генерацию `capabilities.md`, записать source commit/hash.
- Исправить ценовые тесты: расчёт проверять на контролируемых fixtures; соответствие живого каталога тестировать отдельно.
- Расширить payload validation: required media arrays, количество файлов, enum types, конечные числа, диапазоны, размеры и межполевые ограничения.
- Добавить конфигурацию, секреты, structured errors, SQLite migrations и capabilities.

Выход: MCP запускается в чистой установке; `tools/list` и read-only tools проверены; stdout содержит только протокол; тесты проходят без ключей.

### Этап 2. Реализовать графовый редактор

- API JSON import/export, внутренние схемы и каталог поддержанных нод.
- Все обязательные node/edge/model operations и атомарные batch edits.
- Блоки, revisions, diffs, dependency-aware validation.
- UI JSON import/export для известного набора нод; явные ошибки для остальных конструкций.

Выход: агент может создать граф с нуля, вставить новый блок, удалить ноду и перенаподключить зависимости; некорректная операция не портит предыдущую версию.

### Этап 3. Проекты и выбор workflow

- Регистрация проектов, индексация документов/assets и нормализация сцен.
- Библиотека минимум из нескольких различающихся workflows: изображение по тексту, изображение с референсами, видео из изображения; start/end или multi-reference режим включать по реально доступным схемам.
- Метаданные совместимости, фильтрация и краткий отчёт выбора.
- Перенос выбранных upstream examples только после проверки форматов и облачных зависимостей.

Выход: команда с номером сцены разрешает контекст и референсы без ручного ввода node IDs и промпта пользователем.

### Этап 4. Исполнение и восстановление

- Upload/cache, финальная компиляция графа и сохранение payload.
- Асинхронный Workflow API submit/status/outputs/cancel adapter.
- Защита от повторной отправки, `SUBMIT_UNKNOWN`, восстановление после закрытия клиента.
- Скачивание и техническая проверка результатов, понятные ошибки недостающих нод/моделей.
- LoRA upload flow и привязка к `RHLoraLoader`: offline tests обязательны, live-приёмка — на доступном профиле. Если upstream/backend не поддерживает операцию для профиля, вернуть `unsupported` и явно отметить ограничение поставки.

Выход: изменённый workflow создаёт изображение и видео через RunningHub; клиентский таймаут не запускает дубликат; результаты сохраняются в правильном проекте.

### Этап 5. Проверка пользователем и полный сценарий

- Review gate, версии отзывов, approved dependencies.
- Inline preview/resource links и отчёт технического/визуального QC.
- Исправление сцены по комментарию без потери предыдущей версии.
- Блокировка следующего производственного запуска до ответа пользователя, включая low-level tools.

Выход: цикл «сцена → самостоятельная подготовка → генерация → показ → ожидание → правка/утверждение» проходит целиком.

### Этап 6. Поставка и проверка переносимости

- Установка на Windows, фиксированные зависимости, пример конфигурации без секретов.
- Smoke test через реальный MCP-клиент, включая прерывание и повторное подключение.
- Второй тестовый проект с другими именами сцен и assets для проверки универсальности.
- Документация поддерживаемых классов, backend capabilities, ограничений и восстановления задач.

Выход: воспроизводимая установка, полный acceptance, отсутствие зависимости от конкретного проекта Gen2.

### Последующее расширение

Прямой Standard Model API, дополнительные schema adapters, автоматизированное обновление каталогов, продвинутые операции с LoRA сверх описанного upload flow и proxy discovery. Эти расширения не должны задерживать обязательное редактирование и выполнение графов. Браузерный Workspace CRUD остаётся отдельным вариантом развития.

## 16. Приёмочные проверки

| Проверка | Ожидаемый результат |
| --- | --- |
| Создать workflow с нуля | Валидный граф запускается в RunningHub |
| Добавить ноду и соединить её | Новый участок действительно влияет на путь исполнения |
| Удалить ноду с потребителями | Требуется корректный reconnect; висячая связь не попадает в submit |
| Заменить модель другого семейства | Связанные ноды адаптируются либо возвращается точный конфликт |
| Вставить/удалить блок | Внешние порты и результаты сохраняют заданную семантику |
| Добавить несколько референсов | Порядок, роли и лимиты совпадают с требованиями выбранного режима |
| Импорт UI JSON с неизвестной custom node | Конкретная ошибка, исходник сохранён, нет молчаливой потери части графа |
| `02b` в проекте A и B | Выбраны разные правильные сцены и файлы без смешивания |
| Изменён asset/требование или отменён plan после prepare | Неактуальный план не запускается; новая соседняя revision сама по себе не меняет snapshot |
| Сетевой timeout после submit | Нет слепой повторной платной отправки |
| Закрытие MCP во время видео | После старта восстановлен известный job, скачан его результат |
| HTTP 200 с прикладной ошибкой | Ошибка не считается успешной задачей |
| Известный `skip_error` или обработчик ошибки API-ноды | Перед submit `skip_error=false`, ошибка распространяется; неизвестные opaque-заглушки не обещать распознавать по картинке |
| Готовый результат | Пользователь видит preview, состояние — `PENDING_REVIEW` |
| Попытка следующего запуска до отзыва | Общий review gate отклоняет её |
| Замечание пользователя | Создаётся новая версия, старая сохранена |
| Утверждённый файл заменён по тому же пути | Старое утверждение не действует для новых bytes |
| Изменение upstream каталога | Старые workflow revisions не меняются автоматически |

Модульные тесты графов и state machine выполнять без сети. API contract tests — на очищенных fixtures; реальные интеграционные пробы обозначать отдельно. Не считать mock tests доказательством работоспособности backend.

Для исходного MCP-аудита проведены установка зависимостей во временном checkout с отключёнными install scripts, TypeScript build и существующие 7 MCP tests. Python-тесты, настоящий stdio handshake, custom nodes runtime и платные API в рамках исследования не проверялись.

## 17. Приоритеты и открытые вопросы

Первый приоритет — доказать cloud execution структурно изменённого графа. Второй — реализовать надёжное редактирование. Каталог моделей upstream сокращает работу над discovery, но не устраняет эти задачи.

Вопросы для проверки реализацией, без необходимости заново выбирать архитектуру:

- Какие классы нод и модели действительно доступны в целевом RunningHub-профиле?
- Принимает ли full-graph submit новый граф без сохранённого workflow ID?
- Есть ли доступный remote node discovery и какие маршруты proxy реально работают?
- Какие примеры upstream можно исполнять в облаке без передачи ключей внутри графа?
- Какие размеры upload, способы отмены и сроки доступности результатов действуют для выбранного API?
- Какие preview/resource types поддерживает фактический MCP-клиент пользователя?

Вопросы, требующие пользовательских данных при подключении: выбранный профиль/ключ, корень производственного проекта, источники workflow или разрешение выбрать стартовую библиотеку, желаемые лимиты. Не спрашивать повторно то, что уже задано в проекте или текущем диалоге.

## 18. Отношение к прежнему исследованию

Из `official-mcp-bridge-snapshot-20260906.md` сохранены полезные идеи: локальные версии, разделение API families, фиксация происхождения графа, восстановление задач и отделение Workspace от per-run исполнения.

Bridge-first архитектура не выбрана: найденная TypeScript MCP-база позволяет создать единый сервер без обязательной связки с локальным `comfy-cli`. Ограничение прежнего исследования только изменением slots не соответствует текущему запросу на добавление/удаление нод и связей.

Обязательное отдельное подтверждение каждого платного запуска из старого документа не переносится в обычный пользовательский процесс. Применяется согласованный режим: пользователь просит генерацию, агент выполняет её в пределах разрешённой задачи, показывает результат и ждёт проверки.

Само старое исследование и приложенный производственный план используются как справочные материалы. Исторические node IDs, конкретные персонажи и ранее предложенные инструкции не являются обязательными настройками нового универсального MCP.

## 19. Критерий завершения проекта

Реализация завершена, когда пользователь может подключить новый проект и одной командой на сцену получить изображение или видео через RunningHub; агент самостоятельно выбирает и при необходимости структурно меняет ComfyUI workflow; точные входы и результат сохранены; после показа система ожидает ответ пользователя; повторный запуск после ошибки связи не создаёт случайных дубликатов.

Наличие только каталога API-моделей, работающего `rh_run_model` или генерации по фиксированным templates не удовлетворяет этому критерию.

## 20. Контракты, которые нельзя оставлять на усмотрение реализации

### 20.1. Минимальная модель данных

Это проектируемые типы нашего сервера; они не являются схемой RunningHub. Все IDs непрозрачные строки. Поля времени — UTC ISO 8601. Каждая persisted JSON-структура имеет `schema_version`; несовместимую версию отклонять до изменения данных.

| Сущность | Обязательные поля/инварианты |
| --- | --- |
| `Project` | ID, canonical root, backend profile ID, документы, asset roots, output root, policy revision |
| `Scene` | project/scene IDs, aliases, action text, output kind, constraints, required asset roles, dependencies, sources hash |
| `Asset` | project/asset IDs, relative path, content hash, MIME, размер, roles, source, usage policy, review reference при наличии |
| `NodeSchema` | class type, schema revision, input schemas, output index/type list, source evidence, backend scope |
| `WorkflowRevision` | project/workflow IDs, revision ID, parent revision, graph blob hash, schema references, bindings, validation report |
| `BlockDefinition` | block/revision IDs, nodes, exposed inputs/outputs, parameter bindings, dependency constraints |
| `WorkItem` | server ID, project/chain IDs, scene ID, user request, request kind, allowed outputs/stages, state |
| `ExecutionPlan` | server ID, work item ID, graph revision/hash, ordered asset bindings/hashes, requirements/policy hashes, backend profile, output contract, mode |
| `Job` | ID, unique plan ID, request ID, execution/provider/artifact states, provider task ID, submit intent, attempts, timestamps |
| `ReviewEvent` | event ID, job/result ID, exact output hash, decision, feedback, user message reference, timestamp |

Для `Scene.constraints` отделить обязательные ограничения от предпочтений. Например, обязательный конечный кадр нельзя превратить в необязательный ради доступной модели. Missing/unknown данные не превращаются в false или 0.

Результат может содержать несколько output files, включая технические вспомогательные выходы. `output_contract` обозначает, какой файл/набор является пользовательским deliverable и какие output node IDs ожидаются. Выбирать «первый URL в ответе» недостаточно. `review_group_id` объединяет несколько явно запрошенных вариантов, если такой пакет разрешён.

### 20.2. Входы графа и операции

Внутренние значения входов имеют явный discriminant. Сокращённая спецификация:

```typescript
type InputValue =
  | { kind: 'literal'; value: JsonValue }
  | { kind: 'integer'; decimal: string }
  | { kind: 'link'; node_id: string; output_index: number }
  | { kind: 'asset'; asset_id: string; representation: string };

type ValidationReport = {
  structural: 'valid' | 'invalid';
  runnable: 'ready' | 'draft' | 'invalid';
  backend_compatibility: 'verified' | 'unknown' | 'unsupported';
  issues: Array<{
    code: string; severity: 'error' | 'warning';
    node_id?: string; input_name?: string; message: string;
  }>;
};
```

`JsonValue` здесь — обычное JSON-значение с конечными безопасными числами; большие целые идут через `kind: integer`. Эта запись — спецификация, не готовый компилируемый модуль. В рабочем коде определить тип полностью и соответствующие runtime validators.

Неподключённые inputs отсутствуют в map. Один порт имеет максимум одно значение; `connect` с уже занятым портом требует `replace_existing=true`. Список референсов хранится упорядоченными bindings, а не произвольно упорядоченным set.

Минимальный набор полей операций:

- `add_node`: class type, schema revision, optional requested ID, initial inputs.
- `remove_node`: node ID; default `reject_if_referenced`. Для reconnect использовать единый пакет remove/connect, проверяемый целиком; массового неявного cascade delete нет.
- `set_input`: node ID, input name, tagged value; `unset_input` удаляет значение порта.
- `connect`: source node/output, target node/input, replace flag; `disconnect`: target node/input.
- `replace_node`: node ID, replacement class/schema и явный port mapping; сохранять старый ID только если это не нарушает схему.
- `insert_block`: block revision, instance ID, внешние bindings; сервер возвращает выделенные node IDs.
- `remove_block`/`replace_block`: instance ID и стратегия внешних портов.
- `bind_asset`: asset ID, role, target node/input; операция не выполняет upload.
- `set_model`: catalog model ID и loader/блок, known replacement mapping при смене семейства.

`rh_edit_workflow` использует compare-and-swap `base_revision == current_revision`; при конфликте — `REVISION_CONFLICT`, без last-write-wins. Старые revisions никогда не перезаписываются. Пакет с ошибкой не создаёт revision.

Hash исполняемой модели считать из канонического JSON: сортировать ключи объектов, сохранять порядок массивов, не округлять числовые токены. UI coordinates/раскладка не меняют hash исполняемого графа; собственный UI-file hash хранится отдельно. Проверить deterministic hash отдельными перестановочными тестами.

### 20.3. Начальное наполнение библиотеки

Для первого поддерживаемого профиля нужны:

1. API-граф создания изображения по тексту.
2. API-граф изображения с как минимум двумя различимыми референсами либо явно документированным меньшим лимитом; общий редактор должен уметь работать с несколькими bindings.
3. API-граф видео с reference/start image.
4. Один повторно используемый блок, извлечённый из этих схем; тест его повторной вставки без конфликтов IDs.

Графы брать из доступных экспортов/шаблонов; классы и имена весов фиксировать только после чтения их реальных схем. Доступный исходный API-export достаточен для offline graph tests, но сам по себе не подтверждает выходные типы custom nodes или облачное исполнение.

`node_catalog` bootstrap: известные схемы стандартных нод из закреплённого первичного источника + схемы конкретных custom node пакетов стартовых workflows. Для каждого источника сохранить URL/path, revision и преобразование. Если есть работающий remote discovery — дополнить каталог им. Нельзя разблокировать startup поддельным пустым `object_info`.

Модель/нода из неподтверждённого каталога может быть показана кандидатом с `unknown`; пользователю не обещается, что она уже доступна. UI examples upstream импортировать по одному профилю; портирование всех 337 примеров не является целью первой версии.

### 20.4. SQLite и конкурентные вызовы

Минимальные ограничения БД:

- Unique job на `plan_id`; unique `(profile_id, api_family, provider_task_id)` для известного provider ID.
- Unique request key в пределах проекта; повтор с тем же ключом и другим plan возвращает `REQUEST_CONFLICT`.
- Unique revision ID и неизменяемая связь revision → blob hash.
- Один активный work item на review chain; резервирование выполняется в транзакции. Не ограничиваться in-memory mutex.
- Poller owner/lease для одного job, если запущены два процесса MCP; истечение poller lease разрешает возобновить polling, но никогда не повторить submit.

Порядок `rh_run_workflow`:

1. Разрешить request ID и plan ID; вернуть существующий job при корректном повторе ещё до проверки pending review.
2. Проверить plan/work item/project принадлежность, отмену, доступность assets и policy.
3. Атомарно зарезервировать chain и создать job, либо получить конкурентно созданный.
4. Выполнить разрешённые uploads; сохранить окончательный snapshot и его hash.
5. Атомарно захватить единственный переход `READY → SUBMITTING` с submit intent.
6. Отправить один POST; сохранение task ID — следующий durable шаг. Ошибка записи task ID не должна приводить к новому POST.
7. Перейти к наблюдению и скачиванию. Возврат инструмента/отключение MCP transport не должен отменять remote job автоматически.

| Момент сбоя | Поведение после восстановления |
| --- | --- |
| До создания submit intent | Продолжить локальную подготовку; платной отправки ещё не было |
| Intent записан, task ID неизвестен | `SUBMIT_UNKNOWN`; никаких автоматических повторов |
| task ID записан | Polling существующей задачи |
| Remote success, файл не скачан | Повторить получение outputs/download, без generation |
| Файл скачан, manifest не опубликован | Проверить hash, допубликовать manifest/outbox |
| Отзыв записан, ответ MCP потерян | Повтор отзыва идемпотентен по review event/request ID |

`rh_work_item create` сохраняет запрос со статусом `REQUESTED`, но не создаёт job и не списывает лимит генерации. Production chain по умолчанию одна на проект; новую независимую цепочку создавать только для явно отдельного пользовательского задания. Активную reservation для исполнения/проверки устанавливает execution service. `close` может закрыть неисполнявшийся запрос; running/unknown job сначала требует корректного cancel/reconcile, а pending review — отзыва или явно зарегистрированного переключения пользователем.

Отмена до submit отменяет локальный plan и освобождает его work item. После submit отмена относится к конкретному provider task ID и не означает подтверждённого `CANCELLED`, пока backend это не доказал. Если cancel API не поддержан, вернуть `CAPABILITY_UNSUPPORTED`; не вызывать глобальный interrupt чужих задач.

### 20.5. Review и технические ошибки

Разрешённые причины следующего work item в существующей цепочке: новая команда пользователя после завершения предыдущего задания, явная просьба исправить результат либо заранее заданное продолжение последовательного пакета после утверждения.

Для неизвестной отправки, незавершённого download и неоднозначной отмены chain не освобождать автоматически. Для подтверждённого terminal failure показать диагностику; исправления графа локально допустимы, новая платная попытка должна соответствовать запросу пользователя и политике retries. По умолчанию число автоматических новых платных попыток — 0.

Повтор polling/download не считается новой генерацией. Review-состояние появляется только после сохранения deliverable. Не создавать `PENDING_REVIEW` для пустого массива outputs, JSON ошибки, HTML страницы или thumbnail вместо ожидаемого master-файла.

Для нод, умеющих скрывать ошибку, graph profile требует `skip_error=false` или проверенную альтернативу. Универсально отличить непрозрачную error-image от обычного результата по одним bytes нельзя; эту границу указать в QC, а не реализовывать ненадёжный детектор «картинка выглядит как ошибка».

### 20.6. Ошибки и исходящие запросы

Минимальные стабильные коды: `PROJECT_NOT_FOUND`, `SCENE_AMBIGUOUS`, `ASSET_MISSING`, `ASSET_CHANGED`, `SCHEMA_UNKNOWN`, `INVALID_GRAPH`, `REVISION_CONFLICT`, `MODEL_INCOMPATIBLE`, `CAPABILITY_UNKNOWN`, `CAPABILITY_UNSUPPORTED`, `PLAN_STALE`, `REVIEW_PENDING`, `REQUEST_CONFLICT`, `SUBMIT_UNKNOWN`, `PROVIDER_ERROR`, `DOWNLOAD_FAILED`.

`rh_asset upload` не разрешает arbitrary file path: asset должен принадлежать project/work item и профилю. Обычный workflow upload возвращает tagged `provider_file`, а V2 upload — tagged `provider_url`; codec не допускает их взаимозамену. LoRA имеет собственный tagged reference и adapter.

Ссылки для download брать из результата выбранного backend, проверять redirect destinations и конечные размеры. Auth headers провайдера не пересылать на посторонний CDN автоматически. Пользовательские filenames не использовать как абсолютные пути сохранения.

Сеть выполняется только через backend clients. Документы, metadata и tool descriptions не могут запускать HTTP или код при импортировании. Не переносить `eval`/`exec` произвольных выражений для цен/нод из внешних JSON.

- Проверить установку и реальный MCP handshake из чистого временного профиля. К существующей конфигурации клиента добавлять новый сервер, не затирая другие записи и не отключая пользовательские серверы без запроса.
- Готово: обязательный acceptance заполнен доказательствами. При недоступном внешнем тесте результат — частичная реализация с явным `LIVE_PENDING`, не «проект завершён».

## 22. Доказательства, журнал и завершение

### 22.1. Формат контрольного журнала

`PROGRESS.md` — обязательный активный журнал прогресса в корне проекта. Он содержит текущую сводку, статусы L00–L08, handoff, ограничения и следующий конкретный шаг; полная историческая хронология может находиться в явно связанном immutable archive под `docs/`. В новом контексте сначала читать `PROGRESS.md`, а затем релевантные разделы спецификации; archive открывать только для исторического контекста. Не создавать параллельный активный журнал статусов.

Существенным шагом считается реализованная операция/контракт, завершённая часть модуля, миграция БД, исправление ошибки, интеграция зависимости, проверка API, значимый результат тестирования или решение, меняющее реализацию. Запись нужна сразу после такого шага, включая неуспешный результат и блокировку, а не только после завершения пакета. Каждую команду чтения файлов отдельно протоколировать не требуется.

Для каждой записи указывать:

1. Уникальный ID шага, дату, пакет L00–L08 либо метку подготовки и статус.
2. Что фактически изменено и зачем; относительные пути затронутых файлов/модулей.
3. Какие проверки/команды действительно выполнены и их результат; непроведённые проверки обозначить явно.
4. Доказательства: test output, fixture, manifest или ссылка на запись в `ACCEPTANCE.md`/`DECISIONS.md`, если они уже существуют.
5. Оставшиеся ограничения, незаконченные действия и следующий конкретный шаг.

Сводку можно обновлять; исторические записи сохранять. Исправление прежнего вывода оформлять новой записью со ссылкой на исходную. Не отмечать пакет `DONE` до выполнения его критериев и не считать планирование реализацией кода. Не записывать ключи, токены, приватные payload и подписанные URL. Перед завершением/передачей сессии обязательно сверить журнал с реальным состоянием файлов и тестов.

`DECISIONS.md` хранит только новые технические решения с основанием. Уже зафиксированную архитектуру не пересматривать из-за удобства модели. Новые данные API могут изменить способ реализации; изменение пользовательского результата должно быть явно согласовано.

`ACCEPTANCE.md` содержит для каждой проверки раздела 16 и пакетов: ID, вид (`unit`, `synthetic_contract`, `recorded_contract`, `mcp`, `live`), статус, evidence path и ограничение вывода. Не использовать общий «tests passed» вместо этих данных.

Fixture manifest указывает `origin=synthetic|recorded`, upstream/backend revision, дату, профиль без секретов и список очищенных полей. Синтетический ответ никогда не становится `recorded` после простого успешного теста парсера.

### 22.2. Ожидаемые команды проверки

После реализации scripts в L01 стандартный набор:

```text
npm run typecheck
npm run build
npm run test:unit
npm run test:contract
npm run test:mcp
npm run test:acceptance:offline
```

`npm run test:live` — отдельный opt-in запуск с профилем и конкретными разрешёнными cases. В обычные тесты не включать автоматическую загрузку данных пользователя или вызовы, списывающие баланс. Windows-инструкции должны учитывать использование `npm.cmd`, если запуск `npm.ps1` ограничен локальной политикой.

Тесты проверяют поведение, а не наличие файлов/названий функций. Для графов сравнивать структуру и семантику, для recovery — количество сетевых submit и сохранённые states, для MCP — реальный транспорт, для изображения/видео — полученный артефакт и контракт его выходов.

### 22.3. Что обязательно сообщить при передаче результата

- Что реализовано и какие команды действительно выполнены.

- Какие проверки не запускались и почему; отсутствие ключа не скрывается за mock success.
- Где находятся результаты, manifest, instruction для агента и инструкция подключения.
- Какие конкретные действия остались до критерия раздела 19.
