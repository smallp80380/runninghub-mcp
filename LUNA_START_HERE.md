# Начальная инструкция для GPT-5.6 Luna

Задача: реализовать самостоятельный MCP RunningHub по выбранному пользователем варианту 2. Спецификация: [RUNNINGHUB_MCP_IMPLEMENTATION_PLAN.md](RUNNINGHUB_MCP_IMPLEMENTATION_PLAN.md), редакция 2. Этот файл задаёт порядок работы; подробные контракты находятся в спецификации.

## Результат, который нужен пользователю

Пользователь называет проект и сцену. Агент читает сюжет/план, выбирает workflow, при необходимости добавляет/удаляет ноды и блоки, меняет модели/связи/промпты, загружает референсы и запускает граф в RunningHub. После генерации показывает результат и ждёт ответа пользователя. Новый проект не требует переписывания MCP.

## Зафиксированные решения

- Основа: TypeScript MCP из `HM-RunningHub/ComfyUI_RH_OpenAPI/developer-kit/mcp-server`, commit `6dc03fd9655bb8729a561c5f5a1f73c4b285081d`; это read-only база, её нужно расширить.
- Обязателен cloud backend полного ComfyUI graph execution. Основной кандидат — Workflow API; native proxy допустим по результатам проверки.
- Прямой Standard Model API — необязательное расширение. Им нельзя заменить поддержку графов.
- Runtime: Node.js/TypeScript, MCP SDK, строгие схемы, SQLite, локальные JSON/media artifacts. Локальная GPU и импорт Python ComfyUI-плагина не требуются.
- Обязательный graph editor: API import/export, создание с нуля, nodes/edges, blocks, model compatibility, revisions и validation. Поддержка UI JSON ограничена явными schema profiles.
- Утверждение качества происходит после генерации. Обычную команду пользователя на генерацию не превращать в повторные вопросы о каждом техническом шаге.

## С чего начать

1. Проверь текущие файлы и рабочее дерево. Не перезаписывай существующие изменения.
2. Прочитай `PROGRESS.md` и продолжи с указанного незавершённого шага/пакета.
3. Прочитай разделы 0–5, 18–19 и очередь пакетов в разделе 21 спецификации. Контракты конкретного пакета читай по его указателям.
4. Начни с L00. Выполняй L00–L08 последовательно; после проверенного пакета продолжай следующий без лишнего запроса разрешения.
5. Поддерживай существующий `PROGRESS.md`; создай `ACCEPTANCE.md` и `DECISIONS.md` по плану. После каждого существенного шага реализации записывай в `PROGRESS.md` изменения и файлы, выполненные проверки и результат, ограничения и следующий шаг. Не жди завершения всего пакета; сохраняй историю и не создавай второй журнал статусов.

Не нужно сначала перечитывать весь архив исследования или все 337 upstream examples. Прежнее исследование — справочный материал; требования этой спецификации актуальнее исторических предложений.

## Правила, предотвращающие ошибки реализации

- Draft graph разрешён; runnable graph проверяется перед submit. Нельзя запрещать сохранить пустой черновик и затем требовать построения графа по нодам.
- API-schema, ComfyUI node-schema и доступность класса в облаке — разные сведения. Не выводи одно из другого.
- Большие IDs и seed сохраняй lossless. Перевод в строку после округления обычным JSON.parse уже не помогает.
- Один plan — один job. При потерянном ответе submit не выполняй второй платный POST.
- Старые workflow revisions и results immutable. Изменения создают новые версии.
- Review gate работает через общую chain/work-item модель и БД во всех submit paths.
- `SUCCESS` провайдера не равно `APPROVED` пользователя. Отзыв привязан к конкретному output hash.
- Пустые outputs, заглушки, mock-ответы и неисполняемые fixtures не являются успешной cloud generation.
- Для неизвестной возможности возвращай `unknown`/`unsupported` с причиной. Не создавай вымышленные endpoints, node IDs, имена весов или схемы.

## Если нет ключа или доступа к RunningHub

Продолжай offline-пакеты, tests и подготовку probe runner. Пометь live cases `NOT_RUN`/`LIVE_PENDING`. Не объявляй весь проект готовым и не останавливай независимую работу. Для внешней проверки запрашивай только недостающие данные; не проси присылать секрет в текст чата, предложи настройку профиля/окружения.

Команда реализовать MCP не равна разрешению на произвольную серию платных проб. Перед live cases используй уже данное пользователем разрешение и лимиты либо запроси недостающую конкретную авторизацию. Обычный производственный запуск по явной команде пользователя не требует повторного подтверждения.

## Как завершать рабочую сессию

Сверь `PROGRESS.md` с фактическим состоянием: существенные шаги записаны, сводка пакетов актуальна, tests/результаты и непроверенные случаи указаны, следующий файл/функция/проверка определены. Сообщи пользователю конкретно, что работает и что остаётся. Не выдавай локальную готовность за live acceptance.
